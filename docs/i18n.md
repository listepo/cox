# Localization (i18n)

cox keeps its user-facing strings in [Fluent](https://projectfluent.org/)
(`.ftl`) files. The Rust side formats them at runtime with `fluent-bundle`; the
native desktop apps get the same strings as platform resource files generated
by `ftl-export`. Fluent is the single source of truth: never edit a generated
`.strings`, `.stringsdict` or `.resw` file.

Status: groundwork. The crate, the locales and the export exist; no surface
(TUI, CLI, macOS app) reads from them yet.

## Languages

| Code | Language | Plural categories | Role |
| --- | --- | --- | --- |
| `en` | English | `one`, `other` | source, default and fallback |
| `ru` | Russian | `one`, `few`, `many`, `other` | translation |
| `uk` | Ukrainian | `one`, `few`, `many`, `other` | translation |

Codes are BCP 47 language subtags, the same in the folder name, the Fluent
language id and the Apple `<code>.lproj`; Windows folders add the region
(`en-US`, `ru-RU`, `uk-UA`).

## Layout

```
crates/cox-i18n/
  locales/README.md       how to add a locale
  locales/en/main.ftl     every message id, first
  locales/ru/main.ftl
  locales/uk/main.ftl
  src/lib.rs              embedding, negotiation, fallback, t() and tr!
  src/export.rs           Fluent -> .strings / .stringsdict / .resw
  src/bin/ftl-export.rs   the export command
```

The `.ftl` files are embedded with `include_str!`, so the binary needs no
files at runtime. They live inside the crate (not at the repository root) so
the crate stays self-contained.

## Adding or changing a string

1. Add the message to [`locales/en/main.ftl`](../crates/cox-i18n/locales/en/main.ftl)
   with a comment describing each variable (`# $count (number): …`).
2. Add translations to `ru` and `uk`. A missing translation is not an error:
   the message resolves from `en` (see below), and the export fills it in.
3. Plurals are a select on a numeric variable whose keys are CLDR categories,
   with `*[other]` as the default:

   ```ftl
   session-count = { $count ->
       [one] { $count } сессия
       [few] { $count } сессии
       [many] { $count } сессий
      *[other] { $count } сессии
   }
   ```

4. Shared names (the product name) are terms, `-brand-name = Cox`, used as
   `{ -brand-name }`.
5. Run `cargo test -p cox-i18n`: it checks every locale parses, that no
   translation defines an id `en` lacks, and the plural forms.

## Rust usage

```rust
use cox_i18n::{tr, t, FluentArgs, Localizer};

// Process-wide, negotiated from the env and OS on first use.
let title = tr!("settings-title");
let count = tr!("session-count", count = 5);
let welcome = tr!("welcome-user", name = "Ivan");

// Or explicitly, e.g. in tests or for a per-session language.
let uk = Localizer::for_tags(&["uk-UA"])?;
let mut args = FluentArgs::new();
args.set("count", 21);
assert_eq!(uk.format("session-count", Some(&args)), "21 сесія");
```

- **Negotiation.** The requested languages are the POSIX message locale
  (`LC_ALL`, then `LC_MESSAGES`, then `LANG`; `uk_UA.UTF-8` is understood,
  `C`/`POSIX` are ignored) followed by the OS UI languages (`sys-locale`; a
  GUI app has no `LANG`). They are matched by language against `en`, `ru` and
  `uk` (`fluent-langneg`, filtering), so `uk-UA` selects `uk`. `en` always
  ends the chain.
- **Per-message fallback.** A `Localizer` holds one bundle per locale in the
  chain, for example `[uk, en]`. Formatting walks the chain and uses the
  first bundle that has the message, so a message missing from `uk` comes
  from `en` while every other message stays Ukrainian.
- **Missing keys.** An id no locale defines renders as the id itself
  (`format`), so it is visible in the UI; `try_format` returns `None`.
- **Arguments.** Pass numbers as numbers (`count = 5`, not `"5"`), or the
  plural select falls through to `other`. Unicode isolation marks around
  placeables are off: cox ships no right-to-left locale.

## Native export

```
cargo run -p cox-i18n --bin ftl-export            # writes target/i18n/
cargo run -p cox-i18n --bin ftl-export -- --out <dir>
```

Output (under `target/`, gitignored; never commit it):

```
target/i18n/apple/{en,ru,uk}.lproj/Localizable.strings
target/i18n/apple/{en,ru,uk}.lproj/Localizable.stringsdict
target/i18n/windows/Strings/{en-US,ru-RU,uk-UA}/Resources.resw
```

Messages a translation lacks are written into its files from `en` (marked
`fallback: en` in the comment), because neither Foundation nor the Windows
resource loader falls back per key the way the Rust side does.

### macOS: `.strings` + `.stringsdict`

Plain messages go to `Localizable.strings`, plural selects to
`Localizable.stringsdict`. Why not a String Catalog (`.xcstrings`): a catalog
is an editable source that Xcode rewrites on every build (string extraction,
state tracking), which fights a generator that owns the file; the app has no
catalog or `.lproj` yet; and the legacy pair is per-language, plain, and
checkable with `plutil -lint`. Foundation still reads them on macOS 26.

Mapping:

- Fluent id -> key, unchanged (`String(localized: "session-count")`).
- `{ $name }` -> `%@`; a variable used as a select selector or in `NUMBER()`
  -> `%lld`. With two or more variables, specifiers are positional
  (`%1$@ … %2$lld`), numbered by first appearance in the `en` message, so a
  translation may reorder them.
- Terms and message references are inlined as text; a literal `%` becomes
  `%%`.
- A select becomes `NSStringLocalizedFormatKey = "…%#@count@…"` with one
  string per CLDR category.

Hooking it into the build: `scripts/desktop/app.sh` should run
`cargo run -p cox-i18n --bin ftl-export -- --out desktop/macos/build/i18n`
before `xcodegen generate`, and `desktop/macos/project.yml` should list
`build/i18n/apple` as a resource folder of the `Cox` target (XcodeGen turns
each `<code>.lproj` into a variant group; `CFBundleDevelopmentRegion` is
already `en`). A pre-build script phase would also work, but running it in
`app.sh` keeps Xcode free of a cargo dependency. Not wired yet.

### Windows: `.resw`

One `Strings/<tag>/Resources.resw` per locale, the layout a WinUI 3 project
(`desktop/windows/`, planned in P58) picks up with `ResourceLoader`.

- `{ $name }` -> `{0}`, `{1}`, … in `en` first-appearance order, for
  `string.Format`; literal braces are doubled.
- **Plurals: `.resw` has none.** A select becomes one entry per category,
  `session-count_one`, `session-count_few`, `session-count_many`,
  `session-count_other` (only the categories the locale's message has). The
  app picks the category for the number with ICU's plural rules (Windows
  ships ICU, `icu.dll`) and falls back to `_other` when an entry is missing.
- Hooking it into the build: an MSBuild `BeforeBuild` target runs the export
  into the project's `Strings/` folder (or copies from `target/i18n/windows`).

### What the export accepts

Messages with at most one select, on a variable or `NUMBER($var)`, whose keys
are CLDR categories (`zero`, `one`, `two`, `few`, `many`, `other`; `[0]` maps
to `zero`) with `*[other]` as the default; variables, string and number
literals, terms and message references without arguments. It rejects nested
selects, other functions, term arguments and attributes, and a translation
that uses a variable the `en` message does not have. Message attributes are
skipped. The Rust runtime accepts all of Fluent; these limits only apply to
strings that must reach a native app.
