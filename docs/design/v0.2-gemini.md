# Design: Gemini provider scope gate (T19.3)

## Problem

`roadmap.md` lists Gemini for v0.2. The A9 registry already distinguishes two
integration types: type-1 (native `Provider` impl per wire protocol) vs type-2
(compatible preset over the shared Chat/Responses clients, config lines only).
Gemini must land in exactly one of them.

## The field

Gemini ships two wire shapes: the Gemini API (OpenAI-compatible Chat
Completions endpoint exists) and Vertex AI (own auth, own envelope). Claude
Code and Codex both reach Gemini through the OpenAI-compatible endpoint, not a
native client. Evidence in `research.md` (provider survey) pending re-check at
implementation time.

## cox

Scoped pick: **type-2 compatible preset** (`[providers.gemini]` over the shared
Chat client, `GEMINI_API_KEY`), unless the falsifier fires. Rationale: A9 was
created precisely so DeepSeek/OpenRouter-class additions are config lines; a
`GeminiProvider` struct duplicating the Chat client repeats the mistake A9
fixed. Vertex AI (GCP auth, own envelope) stays out of scope until someone
needs it on paper.

## Falsifiers

1. The OpenAI-compatible endpoint drops a feature the loop needs (streaming
   tool use with signatures, or structured thinking replay) — then Gemini
   promotes to type-1.
2. Auth turns out to need more than a bearer key from env (OAuth dance like
   MCP in T7.6) — then the preset needs an `auth.rs`-shaped companion.

## Review

Gate only: type-2 preset picked; endpoint matrix, model list, and `prices.toml`
rows are the implementation task.
