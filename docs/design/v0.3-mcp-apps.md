# Design: MCP Apps scope gate (T49.4)

## Problem

Estimate the **share of MCP servers** a typical cox user runs whose tools
declare **`_meta.ui.resourceUri`**, and whether the **text/structured tool
result alone** remains usable when the host ignores the UI. Target: if most
servers still return adequate text, a terminal host can **defer iframe
rendering** without blocking real workflows.

## The field

**MCP Apps** (`io.modelcontextprotocol/ui`, stable spec **2026-01-26**): tools
may declare **`_meta.ui.resourceUri`** pointing at a **`ui://`** resource; the
host fetches HTML (often bundled JS/CSS), renders it in a **sandboxed iframe**,
and exchanges JSON-RPC over **`postMessage`** (`ui/initialize`, tool-call
proxying, etc.), with **`_meta.ui.csp`** and **`permissions`** for capability
requests.
(https://modelcontextprotocol.io/extensions/apps/overview.md, checked 2026-09-29;
specification:
https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx,
checked 2026-09-29)

**Client matrix:** MCP Apps are marked supported for Claude Desktop, VS Code
Copilot, ChatGPT, **Cursor**, Goose, Postman, and others; **no terminal-only
MCP host** is listed.
(https://modelcontextprotocol.io/extensions/client-matrix.md, checked 2026-09-29)

**Extensions capability:** clients and servers negotiate optional extensions via
an **`extensions`** field inside
`_meta["io.modelcontextprotocol/clientCapabilities"]` / server capabilities
(extensions overview, checked 2026-09-29). The 2026-07-28 MCP revision
introduced this negotiation pattern for modular extensions (**unverified** for
the exact changelog line "minor change 1" — draft changelog URL returned 404
when checked 2026-09-29).

## cox

cox is a **terminal host** with **no embedded web view**.

| Option | Behaviour | Guard / cost |
| --- | --- | --- |
| **(a) Ignore UI** | Keep displaying the tool's **text/structured result** only — **today's behaviour** for MCP tools in cox | `cox_permission::Engine` already gates `tools/call`; no new listener |
| **(b) Browser bridge** | Serve loopback HTML that implements the host side of the MCP Apps bridge and opens the user's browser | Every app-initiated **`tools/call`** still through **`Engine`**; **new network listener** and CSP review |
| **(c) Forward via ACP** | If a future ACP revision carries MCP App rendering, delegate to the IDE | Depends on ACP + editor; cox stays text-only |

**rmcp:** workspace resolves **`rmcp` 3.4.0** (`Cargo.lock`); cox does not yet
declare or negotiate **`extensions`** / `io.modelcontextprotocol/ui` in the MCP
client path (no matches under `crates/cox-mcp` at gate time).

## Falsifiers

1. Popular servers **stop returning usable text** alongside the UI resource —
   ignoring `_meta.ui` breaks workflows cox users rely on.
2. A **terminal-native** rendering path (e.g. rich TUI widgets driven by MCP
   App metadata without HTML) appears in the spec — revisit option (c) or a
   plugin widget tree (A52).
3. **`rmcp`** exposes Apps host APIs before cox needs them — option (b) becomes
   cheaper to prototype.

## Review

**Verdict: defer** iframe/HTML rendering. **Ship explicitly documented
behaviour (a):** text result only, UI resource ignored until falsifier 1 or
creator requests browser bridge. A later implementation card should add a
regression test that a tool with `_meta.ui.resourceUri` still surfaces text.

Out of scope: loopback browser host, iframe sandbox, `extensions` negotiation
implementation.
