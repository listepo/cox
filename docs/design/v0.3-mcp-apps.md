//! v0.3 scope gate for MCP Apps: what a terminal host does with a tool that
//! ships a `ui://` HTML resource, on paper. No runtime code in this slice.

# Design: MCP Apps scope gate (T49.4)

## Problem

The number: **the share of MCP servers a cox user runs whose tools declare
`_meta.ui.resourceUri`, and, of those, the share whose text result alone
still answers the model and the user.** If the second share is near 100 %,
a terminal host loses nothing that matters by ignoring the UI. Neither share
was measured for this gate (no server survey, no network in this pass):
**unverified**. The measurement is a sample of popular servers' `tools/list`
and one `tools/call` each, compared text-only versus with UI.

## The field

- **MCP Apps**: a tool declares `_meta.ui.resourceUri`; the host fetches the
  HTML `ui://` resource and renders it in a sandboxed iframe, talking
  JSON-RPC over `postMessage` (`ui/initialize`, tool calls proxied back to
  the host); CSP and permissions travel in `_meta.ui`
  (https://modelcontextprotocol.io/extensions/apps/overview, checked
  2026-09-28 — as recorded in the P49 card; not re-fetched for this doc).
  Spec: https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx
  (checked 2026-09-28 per the card). **Commit not pinned**: no network call
  was made in this pass, so no commit was read.
- **Client matrix**: https://modelcontextprotocol.io/extensions/client-matrix
  (checked 2026-09-28 per the card). Whether any terminal host is listed as
  rendering MCP Apps is **unverified**; the card leaves that to the fetch.
- **Capability negotiation**: the 2026-07-28 spec revision added an
  `extensions` capability field (its changelog, minor change 1, per the
  card). `research.md` §8.1 (field survey, checked 2026-09-22) lists the
  MCP Apps extension as open in cox.
- **rmcp**: 3.4.0, the version in `Cargo.lock`, already exposes it —
  `ClientCapabilities.extensions` and `ServerCapabilities.extensions`
  (`Option<ExtensionCapabilities>`, "SEP-1724"), with its own test declaring
  `io.modelcontextprotocol/ui` with `mimeTypes: ["text/html;profile=mcp-app"]`,
  and `Tool.meta` serialised as `_meta` (local crates.io source,
  `src/model/capabilities.rs` and `src/model/tool.rs`, read 2026-09-29).
  No rmcp bump is needed for any option below.

## cox

**Today.** `cox-mcp` connects with rmcp's default client handler (`()`),
so it declares no `extensions` and in particular not
`io.modelcontextprotocol/ui`; `output_of` in `crates/cox-mcp/src/client.rs`
keeps only the text content blocks and passes `structured_content` through;
a tool's `_meta` is never read. A terminal has no web view. Options:

- **(a) Ignore the UI, keep the text result.** This is today's behaviour,
  stated explicitly: cox never advertises the UI extension, never fetches a
  `ui://` resource, and shows the model and the user the text (and
  structured) result only. A later card makes it test-backed: a scripted
  server whose tool carries `_meta.ui.resourceUri` yields the same
  `ToolOutput` as without it, and the handshake carries no UI extension.
- **(b) Open the `ui://` HTML in the user's browser** through a loopback
  page that implements the host side of the `postMessage` bridge. Every
  app-initiated `tools/call` still goes through `cox_permission::Engine`
  exactly as a model call does, never a page-side allowlist; the HTML is
  untrusted server output served with the CSP from `_meta.ui`. The page is a
  **new network listener** (loopback, per-session token, like the MCP OAuth
  callback in `crates/cox-mcp/src/auth.rs`) and a browser dependency; it
  also breaks headless and ACP surfaces, which have no browser to open.
- **(c) Forward to the editor over ACP**, if ACP ever carries MCP App
  resources — cox would pass the resource through and the editor would
  render it. ACP carrying it is **unverified**; `agent-client-protocol`
  2.2.0 has an `unstable_mcp_over_acp` feature whose scope for UI resources
  was not examined.

Guards: (a) needs none new; (b) keeps `Engine` as the one decider and
`cox_sanitize::sanitize` on any text the page's result puts back into the
transcript; (c) leaves rendering to the editor. No second guard in any
option.

## Falsifiers

1. Popular servers stop returning a usable text result alongside the UI (the
   text becomes "open the app") — then (a) degrades real work and (b) or (c)
   is needed.
2. Servers key their text result on the client's declared extensions, so a
   host without the UI extension gets a worse result than a UI host's
   fallback text — then (a) must at least be measured per server.
3. ACP adds MCP App passthrough — then (c) costs almost nothing and beats
   (b)'s listener.

## Review

**Recommended verdict: build (a) only; defer (b); revisit (c) when ACP
carries App resources** — pending the creator's decision. (a) is today's
behaviour made explicit; it adds no listener, no dependency and no rmcp
bump. §6 amendment draft for the creator: one card in `cox-mcp` — a test
that a tool with `_meta.ui.resourceUri` produces the same `ToolOutput` as
without it and that the client handshake declares no UI extension, plus one
line in the MCP docs saying cox shows the text result only. (b) returns as
its own gate if falsifier 1 fires.

**Creator's verdict (2026-09-29, `plan.md` A123): build (a) only**, as the single card T55.1; (b) deferred; (c) waits for ACP.
