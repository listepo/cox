# Design: remote control scope gate (T49.1)

## Problem

Target: **zero turns abandoned** because the session hit `ApprovalRequired`
while the human was away from the desk and could not answer on the primary
surface — remote control exists to close that gap, not to replace the TUI.

## The field

**Claude Code Remote Control** keeps the session on the local machine; the web
and mobile clients are a window into that process (filesystem, MCP, tools stay
local). It requires a **Claude.ai subscription** (Pro, Max, Team, Enterprise);
the docs state **"API keys are not supported"** for Remote Control and that
the computer must stay on with `claude` running.
(https://code.claude.com/docs/en/remote-control.md, checked 2026-09-29)

**Codex Remote** runs each task on the **connected computer**; the ChatGPT
mobile app pairs via QR code after setup in the desktop app (**Settings →
Connections → Control this Mac or PC**), same ChatGPT account on phone and
desktop, with in-app **approval** of requested commands before work continues.
(https://learn.chatgpt.com/docs/remote.md, redirected from
https://developers.openai.com/codex/remote, checked 2026-09-29)

**ACP — Streamable HTTP & WebSocket Transport** (RFD, stage **Active** since
2026-07-02) standardizes remote ACP over a single `/acp` endpoint (SSE GET
streams + POST, or WebSocket upgrade). **Sessions survive disconnects**; a
client reconnects and resumes via **`session/load`** (v1 does not replay
server→client messages missed while disconnected).
(https://agentclientprotocol.com/rfds/streamable-http-websocket-transport.md,
checked 2026-09-29)

## cox

cox has **no relay service**. **D3** (plan.md §0) allows **API keys only** —
Claude subscription OAuth and undocumented ChatGPT login are out — so a
**vendor-relay design like Claude Code Remote Control or Codex Remote is
rejected**.

**Candidate (build):** extend **`cox acp`** with the RFD's HTTP/WebSocket
transport, listening on **`127.0.0.1` only** by default. The user reaches it
through an **existing tunnel they control** (SSH `-L`, Tailscale Serve/Funnel,
WireGuard) — cox does not open a public inbound port or operate relay
infrastructure. **D2:** the remote client is another consumer of the same
`Event` stream; **`Event::ApprovalRequired`** is answered through the same
`cox_permission::Engine` path the ACP **`request_permission`** handler already
uses (no plugin-side permission checks).

**Auth model:** bind loopback; the tunnel carries TLS or mesh identity the user
already configured. Optional **`--acp-token`** (or env) on the server so even a
local listener requires a shared secret. No subscription login inside cox.

**Alternative (defer as primary):** attach a **second surface to a live TUI
session** via P16 presence records (notify + read-only transcript sync) —
lighter, but does not expose full ACP prompt/approve semantics to a phone
client without more product design.

## Falsifiers

1. The ACP transport RFD **stalls before** a stable SDK/release cox can depend
   on — then remote control stays **stdio-only** until the RFD ships.
2. Users who need remote access **cannot** reach their machine without a
   hosted relay (no SSH, no tailnet) — a loopback+tunnel design does not serve
   them; a hosted relay remains out of scope for cox itself.
3. Tunnel setup friction is high enough that **nobody uses** loopback ACP — then
   the presence-record alternative deserves a separate gate.

## Review

**Verdict: build** (loopback ACP remote transport; no Anthropic/OpenAI relay).
