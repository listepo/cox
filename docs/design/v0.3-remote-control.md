//! v0.3 scope gate for remote control: driving a live cox session from a phone
//! or a second machine, on paper. No runtime code in this slice.

# Design: remote control scope gate (T49.1)

## Problem

A user who walks away from the desk mid-task comes back to a session parked
on an `ApprovalRequired` nobody could answer. Target, not a measurement:
**zero turns lost to an unanswered approval** while the user is reachable on
a phone or a second machine, with the session, its files and its keys still
on the first machine. The field frames remote control exactly this way
(session keeps running locally; the remote end only watches, prompts and
approves); `research.md` §8.1 lists it as table stakes with "none" in the cox
column.

## The field

- **Claude Code Remote Control**: the session stays on the local machine and
  opens only outbound HTTPS; the Anthropic API relays between it and the
  phone/web client; subscription plans only, "API keys are not supported"
  (https://code.claude.com/docs/en/remote-control, checked 2026-09-28 — as
  recorded in the P49 card; not re-fetched for this doc).
- **Codex Remote**: the agent runs on the connected computer, paired from the
  ChatGPT app by QR code, same account on both ends
  (https://learn.chatgpt.com/docs/remote, redirected from
  https://developers.openai.com/codex/remote, checked 2026-09-28 — per the
  P49 card).
- **ACP "Streamable HTTP & WebSocket Transport" RFD**, stage Active; a
  client that loses the connection reconnects and resumes through
  `session/load`
  (https://agentclientprotocol.com/rfds/streamable-http-websocket-transport.md,
  checked 2026-09-28 — per the P49 card).
- The Rust SDK cox builds on, `agent-client-protocol` **2.2.0** (the version in
  `Cargo.lock`), ships no HTTP or WebSocket transport: its feature list has
  only `unstable_*` schema flags and no source file mentions either transport
  (local crates.io source copy, read 2026-09-29). When a release adds one is
  **unverified**; no lead beyond the RFD's stage.
- Amp Orbs and Cursor background agents are listed next to the two above in
  `research.md` §8.1 (survey of 2026-09-22); their mechanics were not
  checked: **unverified**.

## cox

A vendor relay is out: cox runs no relay service, and D3 allows API keys
only, so the one relay that exists for Claude (the Anthropic API behind a
subscription login) is closed to it.

**Candidate A — `cox acp` over the RFD's transport.** `cox acp` already maps
every `Event` to ACP (`crates/cox-acp/src/server.rs`), including
`Event::ApprovalRequired` → `session/request_permission`, whose answer goes
back as the same `Submission` the TUI sends, so `cox_permission::Engine`
stays the one place a call is allowed, denied or escalated (D2: one more
consumer of the event stream). The remote piece is only the transport:
`cox acp --listen 127.0.0.1:<port>` next to today's stdio, and a remote ACP
client (an editor, or a phone client that speaks ACP) reaches it over the
user's own SSH port-forward or Tailscale. Reconnect is `session/load`, which
the server already handles.

**Candidate B — attach a second surface to a live TUI session.** The P16
presence records (`COX_HOME/presence/<session>.json`, A14) already tell one
session about another; a second process could find the TUI's session and
subscribe to its events. This needs a cross-process event channel the core
does not have, and two surfaces answering the same approval; it is the
larger change and only helps a user who started in the TUI.

**Auth model (A).** No inbound port opens by default: `--listen` is opt-in
per run and binds loopback only — a non-loopback address is refused, so
exposing the port is always the tunnel's decision (SSH keys or the tailnet's
identity), never cox's. On top of that, the listener requires a per-run
bearer token written to `COX_HOME` with owner-only permissions and printed
once, so another local user cannot drive the session through the same
loopback port. cox already runs one loopback listener with this shape (the
MCP OAuth callback on `127.0.0.1:0`, `crates/cox-mcp/src/auth.rs`).

Guards: `Engine` covers every approval; `cox_sandbox::sandbox::Policy` and
`cox_sandbox::path::confine` are unchanged because the tools still run on the
first machine; text sent to the remote client is the same event text the ACP
stdio surface sends today. No second guard.

## Falsifiers

1. The ACP transport RFD stalls or is withdrawn before a Rust SDK release
   carries it — then candidate A means hand-rolling a transport the spec may
   change, and the gate reopens.
2. Users cannot reach their machine without a relay (no SSH, no Tailscale,
   managed laptops) — then a loopback listener serves nobody and only a
   hosted relay helps, which this gate rules out.
3. No phone-side ACP client exists to point at the listener — then A only
   serves editor-on-a-second-machine, a much smaller audience.

## Review

**Recommended verdict: defer** — pending the creator's decision. Revisit when
an `agent-client-protocol` release ships the HTTP/WebSocket transport; the
design then is candidate A (loopback-only, opt-in, per-run token, reached
through the user's own tunnel). Candidate B is not recommended. If the
creator chooses **build** now, the §6 amendment draft is: one card for
`cox acp --listen` (loopback refusal, token file, tests over the SDK's
transport) and one for a `cox doctor` line that reports an open listener;
no hosted relay in either.

**Creator's verdict (2026-09-29, `plan.md` A123): defer** until an `agent-client-protocol` release ships the HTTP/WebSocket transport.
