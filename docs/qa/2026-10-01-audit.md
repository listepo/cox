# QA audit: cox (2026-10-01)

Find-only audit. Nothing in this branch changes code; this file is the only change.

## Scope

- Repository: https://github.com/pyrlyn/cox, default branch `main` at `0694a8b7`
  (`ci: notify on release failure (#85)`).
- Areas reviewed: `install.sh`, the V4A patch engine and `apply_patch` tool (`cox-patch`,
  `cox-tools/src/v4a`), `edit`/`write` (`cox-tools`), path confinement (`cox-sandbox/src/path.rs`),
  the permission engine and rule grammar (`cox-permission`), the bash risk classifier

  (`cox-config`), the `memory_save` tool, and the local check scripts (`justfile`, `scripts/`).
- Focus: incorrect implementations, missing input/argument checks, missing error handling,
  anything that reliably errors or breaks, plus security basics (described only, never exploited).
- Out of scope: the macOS desktop app (`desktop/`), the website, providers against live APIs,
  Windows (CI job is disabled), performance.

### F1. `install.sh` cannot install any published release

- **Severity:** high
- **Impact:** the documented installer fails for every user on every platform; nobody can
  install cox with it.
- **Environment:** macOS arm64, `install.sh` at `0694a8b7`, release `v0.1.0`.
- **Steps to reproduce:**
  1. `P=$(mktemp -d)`
  2. `PREFIX=$P/bin sh install.sh v0.1.0`
- **Expected:** `cox` is installed to `$P/bin/cox`.
- **Actual:** `tar: cox: Not found in archive`, exit 1, nothing installed.
- **Evidence:** `tar -tJf cox-aarch64-apple-darwin.tar.xz` lists
  `cox-aarch64-apple-darwin/cox`, `.../README.md`, `.../CHANGELOG.md`. cargo-dist puts files
  under a `cox-<target>/` directory, but the script extracts a top-level member `cox`.
- **Suggested fix:** extract `"cox-${TARGET}/cox"` (or use `--strip-components=1`) and move
  `"$tmp/cox-${TARGET}/cox"`; add a CI smoke test that runs `install.sh` against the latest
  release.
- **Missing check / error handling:** `install.sh:49-50`, which assumes the archive layout
  without checking it.

### F2. `apply_patch` with `*** Move to:` its own path deletes the file

- **Severity:** high
- **Impact:** data loss. A patch the model emits by mistake (`Update File: a.txt` +
  `Move to: a.txt`, or `./a.txt`) writes the new content and then deletes it; the tool reports
  success (`R a.txt -> a.txt`).
- **Environment:** `cox-patch` and `cox-tools` at `0694a8b7`.
- **Steps to reproduce:**
  1. Workspace with `a.txt` = `one\n`.
  2. Call `apply_patch` with
     `*** Begin Patch\n*** Update File: a.txt\n*** Move to: a.txt\n@@\n-one\n+ONE\n*** End Patch`.
- **Expected:** either rejected ("move target equals source") or treated as a plain update.
- **Actual:** `stage` returns `Change { path: "a.txt", from: Some("a.txt"), after: "ONE\n" }`
  (harness output). The tool then runs `atomic_write(a.txt)` and right after it
  `remove_file(a.txt)`, so the file is gone.
- **Evidence:** harness `move_onto_self` output above; `crates/cox-tools/src/v4a/tool.rs:152`
  (write) followed by `:158` (remove `from`).
- **Suggested fix:** in `stage`, reject `move_to == path` after resolution; in the tool, compare
  the confined `PathBuf`s of `path` and `move_to` and skip the removal when they are equal.
- **Missing check / error handling:** `crates/cox-patch/src/apply.rs:96-104` (no
  `move_to != path` check); `crates/cox-tools/src/v4a/tool.rs:156-159`.

### F3. `apply_patch` `*** Move to:` silently overwrites an existing file, without archiving it

- **Severity:** high
- **Impact:** data loss. An existing destination file is replaced, and its old content is never
  archived, so `cox expand`/rewind cannot restore it. This breaks the "lossless" rule in
  AGENTS.md.
- **Environment:** as F2.
- **Steps to reproduce:**
  1. Workspace with `a.txt` = `one\n` and `b.txt` = `precious\n`.
  2. `apply_patch`: `Update File: a.txt`, `Move to: b.txt`, hunk `-one`/`+ONE`.
- **Expected:** refused ("`*** Move to: b.txt` but the file already exists"), the same way
  `Add File` refuses an existing path.
- **Actual:** `stage` returns `Ok` with `before: Some("one\n")` (the source's content);
  `b.txt` is overwritten with `ONE\n`, and only `a.txt`'s content is archived.
- **Evidence:** harness `move_onto_existing` output; archive loop in `v4a/tool.rs` archives
  `c.before` only, which is the source.
- **Suggested fix:** in `stage`, `if let Some(to) = move_to { if read(to).is_some() { Denied } }`.
- **Missing check / error handling:** `crates/cox-patch/src/apply.rs:96-104`.

### F4. Path-based permission rules are matched against the raw, unnormalised model path

- **Severity:** high (security; trust guard)
- **Impact:** `deny`/`ask` rules for path tools can be bypassed by spelling the same path
  differently. With the default `deny = ["Read(~/.ssh/**)", ...]`, a session whose workspace or
  read roots include `$HOME` (cox started in `~`) can still read `~/.ssh/id_rsa` by passing
  `~/.ssh/id_rsa` or `.ssh/id_rsa`. A project rule `Read(.env)` doesn't stop `./.env`. The
  Claude Code form `Read(./.env)` doesn't even match a plain `.env`. Allow rules fail too:
  `Edit(src/**)` doesn't cover `./src/a.rs`.
- **Environment:** `cox-permission` at `0694a8b7`, `globset` 0.4.18.
- **Steps to reproduce:** compile a verbatim copy of `rules.rs::path_globs` with
  `globset = "=0.4.18"`, home `/home/u`, and match:
  1. `~/.ssh/**` against `~/.ssh/id_rsa`, `.ssh/id_rsa` (cwd `/home/u`),
     `/home/u/x/../.ssh/id_rsa`;
  2. `./.env` against `.env` and `/repo/.env`;
  3. `.env` against `./.env` and `sub/../.env`;
  4. `src/**` against `./src/a.rs`.
- **Expected:** every case matches (same file).
- **Actual:** every case prints `matches=false`; only the exact absolute spelling
  `/home/u/.ssh/id_rsa` matches.
- **Evidence:** harness output (9 cases, 1 match). `ToolCall.subject` is
  `tool.subject(&input)`, which is the raw `path` string (`crates/cox-core/src/turn.rs:236,401`;
  `read.rs`/`write.rs` `fn subject`). `confine` normalises the path only later, when the tool
  runs.
- **Suggested fix:** for path tools, give the engine the confined, canonical absolute path (or
  run `confine`/lexical normalisation plus `~` expansion before `decide`), and normalise rule
  patterns the same way (`./x` → `<cwd>/x`). Add table tests for `~/`, `./`, `..` and
  relative-vs-absolute spellings.
- **Missing check / error handling:** `crates/cox-permission/src/rules.rs:103` (glob on raw
  subject), `:132-150` (`./` patterns are not normalised); `crates/cox-permission/src/lib.rs:120`;
  `crates/cox-core/src/turn.rs:236,401`.

### F5. `apply_patch` conflict check compares raw path strings

- **Severity:** medium
- **Impact:** a silently lost edit. Two ops on the same file under different spellings, or a move
  destination that another op also writes, are not caught as "patch touches X twice". The last
  write wins and the summary reports both ops as successful.
- **Environment:** as F2.
- **Steps to reproduce:**
  1. `a.txt` = `one\ntwo\n`; patch `Update File: a.txt` (`-one`/`+ONE`) then
     `Update File: ./a.txt` (`-two`/`+TWO`).
  2. Or: `Update File: a.txt` + `Move to: b.txt`, then `Add File: b.txt`.
- **Expected:** `Denied: patch touches a.txt twice` (or `b.txt`).
- **Actual:** case 1 stages two independent changes from the same original. They are applied in
  `BTreeMap` key order (`./a.txt` then `a.txt`), so the result is `ONE\ntwo\n` and the `TWO` edit
  is lost. Case 2 stages two writes to `b.txt`.
- **Evidence:** harness `same_file_two_spellings` and `move_and_add_same_dest` output.
- **Suggested fix:** key `staged` (and the duplicate check) by the confined path, and include
  `move_to` destinations in the set. `stage` could take a `resolve` closure next to `read`.
- **Missing check / error handling:** `crates/cox-patch/src/apply.rs:63` (only the source path,
  as a raw string); `crates/cox-tools/src/v4a/tool.rs:112-121` (`resolved` keyed by raw string).

### F6. `apply_patch` cannot apply a pure-insertion hunk

- **Severity:** medium
- **Impact:** a hunk with only `+` lines after an `@@ context` header (valid V4A; Codex inserts
  it) always fails, so models trained on V4A keep retrying.
- **Environment:** as F2.
- **Steps to reproduce:** `a.txt` = `one\ntwo\nthree\n`; patch
  `*** Update File: a.txt\n@@ one\n+inserted`.
- **Expected:** `inserted` goes in after `one` (or at the end of file, as Codex does).
- **Actual:** `Denied: hunk 1 matches 4 places (lines 2, 3, 4, 5); add context to make it unique`.
- **Evidence:** harness `pure_insert` output. With `old` empty, every index in
  `from..=lines.len()` matches.
- **Suggested fix:** in `locate`, when `old.is_empty()`, return `from` (the position after the
  `@@` context) instead of searching.
- **Missing check / error handling:** `crates/cox-patch/src/apply.rs:198-199` (no empty-`old`
  branch).

### F7. `edit` accepts an empty `old` and corrupts the file with `replace_all`

- **Severity:** medium
- **Impact:** `{"old": "", "new": "X", "replace_all": true}` puts `X` between every character of
  the file and writes it. Without `replace_all`, it returns an `Ambiguous` error that lists every
  byte position (a huge message for a big file).
- **Environment:** `cox-tools` at `0694a8b7`.
- **Steps to reproduce:**
  1. File `a.txt` = `ab\n`.
  2. `edit {"path":"a.txt","old":"","new":"X","replace_all":true}`.
- **Expected:** `Denied: old must not be empty`.
- **Actual:** content becomes `XaXbX\nX`. `"ab\n".match_indices("")` gives 4 hits, and
  `apply_replace` takes the exact branch.
- **Evidence:** harness output: `matches of empty old: 4`,
  `replace_all with old="": "XaXbX\nX"`. There is no emptiness check between
  `str_field(&input, "old")` and `apply_replace`.
- **Suggested fix:** reject an empty `old` right after reading it; add the schema's
  `minLength: 1`.
- **Missing check / error handling:** `crates/cox-tools/src/edit.rs:94` (and the input schema
  near `:58`).

### F8. `edit`, `write` and `apply_patch` drop the file's permissions (exec bit)

- **Severity:** medium
- **Impact:** editing a script (`run.sh`, `gradlew`, git hooks) makes it non-executable, so the
  next run fails with `Permission denied`. Group/other bits and ACLs are reset too.
- **Environment:** macOS, umask 022.
- **Steps to reproduce:** create `run.sh` with mode 0755 and call `atomic_write` (a verbatim
  copy), which every write path uses.
- **Expected:** mode stays 0755.
- **Actual:** `before: 755`, `after atomic_write: 644`.
- **Evidence:** harness output. `atomic_write` writes a new temp file with default mode and
  renames it over the original (`crates/cox-tools/src/write.rs:57-58`).
- **Suggested fix:** if `path` exists, copy its `metadata().permissions()` onto the temp file
  before the rename.
- **Missing check / error handling:** `crates/cox-tools/src/write.rs:42-63`.

### F9. `cox config set` writes unknown keys and wrongly typed values; then every `cox` command fails

- **Severity:** medium
- **Impact:** one typo bricks the CLI. After `cox config set tiers.code.modle sonnet`, every
  command, including `cox config get` and another `cox config set` to undo it, fails with
  `config error ... unknown field`. The user has to find and hand-edit `~/.cox/config.toml`.
- **Environment:** debug `cox` built at `0694a8b7`, scratch `COX_HOME`.
- **Steps to reproduce:**
  1. `COX_HOME=$(mktemp -d) cox config set tiers.code.modle sonnet`, which exits 0.
  2. `cox config get tiers.code.model`
  3. `cox config set tiers.code.modle x`
  4. Also `cox config set sandbox.network yes`, which exits 0 and writes `network = "yes"`.
- **Expected:** step 1 (and 4) is refused: `no such config key` / `expected a boolean`, and the
  file is left alone.
- **Actual:** the write succeeds. Steps 2 and 3 fail with
  `Error: config error at tiers.code.modle: unknown field: found modle ...`. After step 4,
  `cox config show` fails with `invalid type: found string "yes", expected a boolean`.
- **Evidence:** command output from the run above.
- **Suggested fix:** in `set`/`set_json_in`, build the edited document in memory, run it through
  the same `Config` deserialisation (`deny_unknown_fields`), and write only if that passes.
  Optionally let `config set`/`path` skip the global load in `main.rs:62`, so a broken file can
  still be fixed with the CLI.
- **Missing check / error handling:** `crates/cox-config/src/cmd.rs:113-117` and `:158-185`
  (no schema or type validation); `crates/cox/src/main.rs:62` (a load failure blocks the repair
  command).

### F10. Bash classifier rates file-writing and code-running commands `ReadOnly`

- **Severity:** medium (security; approval bypass)
- **Impact:** `ReadOnly` calls are allowed without asking in the default mode (`by_risk`:
  `Risk::ReadOnly => None`). These commands can overwrite workspace files, or run arbitrary code,
  without the approval a `Write`/`Exec` call needs:
  - `sort -o FILE`, `uniq IN OUT`, `tree -o FILE`, `xxd IN OUT` (or `xxd -r`) all write files;
  - `cargo build|test|check|clippy|doc` run `build.rs`, proc macros and tests (arbitrary code);
  - `npm|pnpm|yarn test` run a `package.json` script.
  The sandbox still limits where they can write, but the approval gate is skipped.
- **Environment:** `cox-tools` at `0694a8b7` (confirmed by reading the code; not run end to end,
  see "Blocked").
- **Steps to reproduce:** call `classify("sort -o README.md README.md")` and
  `classify("uniq a.txt b.txt")`.
- **Expected:** `Risk::Write` (or at least not `ReadOnly`) once an output-file argument is
  present; `cargo`/`npm` test and build commands rated `Exec`, or made an explicit, documented
  product choice.
- **Actual:** `READ_ONLY` contains `sort`, `uniq`, `tree` and `xxd` with no flag inspection.
  `cargo` with `build|test|...` returns `ReadOnly`.
- **Evidence:** `crates/cox-tools/src/bash/classify.rs:21-79` (list), `:368-374` (cargo/npm),
  `:377` (fall-through to `ReadOnly`). Compare `find`, which does check `-delete`/`-exec`
  (`:375`).
- **Suggested fix:** add flag checks like the `find` arm: `sort` with `-o`/`--output`, `tree`
  with `-o`, `uniq`/`xxd` with a second positional argument, `xxd -r` → `Write`. Treat
  `cargo`/`npm` as `Exec`, or record the choice in `plan.md` §0. This one needs a product
  decision.
- **Missing check / error handling:** `crates/cox-tools/src/bash/classify.rs:368-377`.

### F11. `web_fetch` is auto-allowed, has no private-address guard, and redirects skip domain rules

- **Severity:** medium (security; suspected)
- **Impact:** under prompt injection (a fetched page or a repo file telling the model what to
  do), `web_fetch` runs without approval because it is `ReadOnly`. It can reach
  `http://127.0.0.1:<port>`, LAN hosts and `http://169.254.169.254/` (cloud metadata), and can
  exfiltrate data in the query string. A `WebFetch(domain:...)` deny rule is checked only
  against the first URL. reqwest follows up to 5 redirects to any host. There is also no upper
  bound on a model-chosen `max_bytes`, and the scheme check is case-sensitive (`HTTPS://x` is
  refused).
- **Environment:** `cox-tools`/`cox-web` at `0694a8b7`. Read from the code only; no request
  was made.
- **Steps to reproduce (described, not run):**
  1. Default config; deny `WebFetch(domain:evil.example)`.
  2. Model calls `web_fetch {"url": "https://allowed.example/redirect?to=https://evil.example/"}`.
- **Expected:** the redirect target is checked against the domain rules (or redirects to another
  host are refused). Loopback/private/link-local targets need approval.
- **Actual (from code):** `Policy::limited(5)` follows the redirect; the subject is the original
  URL only. There are no IP-range checks anywhere in `cox-web`.
- **Evidence:** `crates/cox-tools/src/web_fetch.rs:51` (`Risk::ReadOnly`), `:66` (scheme check),
  `:71-74` (`max_bytes` from the model with no cap); `crates/cox-web/src/lib.rs:40` (redirect
  policy); `crates/cox-permission/src/lib.rs:245`.
- **Suggested fix:** use a custom redirect policy that re-runs the domain rules and refuses
  loopback/private/link-local/metadata addresses after DNS resolution, unless they are
  allow-listed. Clamp `max_bytes` to a maximum and compare the scheme case-insensitively.
  Whether `web_fetch` should need approval for new hosts is a product decision.
- **Missing check / error handling:** `crates/cox-web/src/lib.rs:36-47`,
  `crates/cox-tools/src/web_fetch.rs:64-75`.

### F12. `edit` rewrites every LF to CRLF in a mixed-line-ending file

- **Severity:** low
- **Impact:** a one-line edit rewrites line endings across the whole file, so the diff is huge and
  the file changes in places the model never touched. A `new` value that already contains `\r\n`
  becomes `\r\r\n`.
- **Steps to reproduce:** file `a\r\nb\nc\n`; `edit old="b" new="B"`.
- **Expected:** `a\r\nB\nc\n`.
- **Actual:** `a\r\nB\r\nc\r\n` (harness, same normalise/restore steps as `edit.rs`).
- **Suggested fix:** convert back to CRLF only when every line was CRLF, or splice on the
  original bytes. Strip `\r` from `new`/`old` before matching.
- **Missing check / error handling:** `crates/cox-tools/src/edit.rs:112-123`.

### F13. `config set` treats an unreadable config file as empty and overwrites it

- **Severity:** low (suspected)
- **Impact:** if the config file exists but can't be read as UTF-8 text (wrong encoding,
  permission error), `set_value_in` uses `unwrap_or_default()`, parses an empty document and
  writes back a file with only the new key. Everything the user had is lost. The CLI path is
  protected only by accident: `main.rs:62` loads the config first and fails. The desktop path
  (`set_json_in`, T37.30) has no such guard.
- **Steps to reproduce (CLI, protected):** write a config with a Latin-1 byte, then run
  `cox config set core.parallel_tools 4`. It fails with `stream did not contain valid UTF-8`,
  and the file is unchanged.
- **Expected:** a read error other than `NotFound` is returned as an error.
- **Suggested fix:** `match fs::read_to_string(path) { Err(e) if e.kind() == NotFound =>
  String::new(), r => r? }`. The same pattern is in `memory.rs::upsert_index` for `MEMORY.md`.
- **Missing check / error handling:** `crates/cox-config/src/cmd.rs:159`;
  `crates/cox-tools/src/memory.rs:257`.

### F14. `just check` fails on `main` (`scripts/leftovers.sh`) and CI never runs it

- **Severity:** low
- **Impact:** the documented local gate (`AGENTS.md`/`justfile` `check`) is red on a clean
  `main`, so contributors learn to ignore it. The leftover audit it enforces has drifted
  silently.
- **Steps to reproduce:** `bash scripts/leftovers.sh; echo $?`
- **Expected:** exit 0 on `main`.
- **Actual:** exit 1 with 463 messages, for example
  `T30.26 (done.md:1134) is in none of the three sets` and
  `T22.10 has a 'Not done:' line but no mapping in this script`.
- **Suggested fix:** update the `closed_by` table / `docs/compat.md` "Known leftovers", then add
  the script to a CI job so it can't drift again. Or drop it from `just check` if the audit is
  retired.
- **Missing check / error handling:** `.github/workflows/ci.yml` (no job runs
  `scripts/leftovers.sh`).

## Checked and not a bug

- `confine` with dangling symlinks: `Path::exists` is false for a dangling link, so the link
  passes `confine`. But `atomic_write` renames over the link itself, and `create_dir_all` fails
  on a dangling directory link, so no write escapes the root.
- `memory_save` races on `MEMORY.md`: the tool is `Concurrency::Exclusive`.

## Blocked

- End-to-end runs of `apply_patch`/`edit`/`write` through `cox mcp --allow-write` were blocked
  by the tool-safety review (classifier error, approval not granted). F2-F8 and F12 are confirmed
  with the standalone harness that compiles the unmodified source files instead.
- `deny`, `audit`, `sandbox-landlock`, `plugin-examples` and `footprint` CI jobs were not run
  (see Run).
